# Project ULPF: Universal Log Pre-processing Framework

**SIH 2026 Problem Statement ID:** 26156

## The Vision (What it's about)
*   **The Baseline:** Modern enterprises generate massive volumes of logs from everywhere—network devices, servers, cloud services, containers, and IoT hardware . 
*   **The Chaos:** The problem is that these logs arrive in wildly diverse formats, including Syslog, JSON, XML, CSV, CEF, LEEF, and weird proprietary vendor schemas . This diversity creates huge bottlenecks for centralized monitoring and security operations .
*   **The Solution:** We are building a Universal Log Pre-processing Framework (ULPF) capable of ingesting, parsing, normalizing, and standardizing logs generated by any hardware or software system . It converts any perimeter network device-generated log into a standardized, analytics-ready representation for next-gen SIEM and cybersecurity platforms . 

## The Hitlist (What needs to be done)
To make this framework a certified W for the judges, we absolutely must hit these specific capabilities :
*   **The Vault:** Preserve the complete raw event data for forensic purposes without any information loss .
*   **The Parser:** Extract and parse source-specific attributes from heterogeneous logs .
*   **The Translator:** Normalize the extracted fields into a single, common event taxonomy .
*   **The Breadcrumbs:** Maintain strict traceability between the newly normalized events and the original raw logs .
*   **The Expansion:** Allow plug-and-play onboarding of completely new log sources to reduce parser development effort for security teams .
*   **The Deployment:** Package the solution in a container so it is platform-independent and deployable in an air-gapped network .

## The Red Flags (What to avoid)
*   **Data Dropping:** Do not alter or lose the original raw event data . It must remain perfectly intact for compliance and forensic investigations .
*   **Cloud Dependencies:** The framework cannot rely on live internet connections or cloud-hosted APIs, because the solution must be deployable in an air-gapped network .
*   **Vendor Lock-in:** The framework must be fully vendor-agnostic .

## The Challenges
*   **Massive Scale:** The system must be suitable for deployment in Big Data environments handling billions of events per day without crashing . 
*   **Data Diversity:** Creating a universal schema that accommodates both current and future data sources across hybrid, multi-cloud, and AI-driven environments . 

## The Procedure
### Step 1: Ingestion & Storage
*   Spin up lightweight **Vector** or **Fluent Bit** listeners to instantly catch incoming logs from any perimeter network device .
*   Configure the listeners to accept massive volumes of diverse formats like Syslog, JSON, XML, CEF, and proprietary vendor schemas .
*   Immediately dump an exact copy of this raw event data into cold storage to preserve it for forensic and compliance purposes without any information loss .

### Step 2: Parsing
*   Funnel the live logs into a heavy-duty message broker like **Apache Kafka** to easily handle billions of events per day without the system crashing .
*   Build plug-and-play Python or Go parser scripts designed for easy onboarding of new log sources .
*   Run the scripts to slice up the heterogeneous logs and precisely extract source-specific attributes from the chaos .

### Step 3: Normalization
*   Map all those freshly extracted fields into a single, common event taxonomy, like the Elastic Common Schema .
*   This transforms the messy data into a unified schema that enables consistent analytics, threat hunting, and anomaly detection .
*   Generate and attach a unique ID to maintain strict traceability between the newly normalized events and the original raw logs .

### Step 4: Containerization
*   Package the entire processing pipeline using **Docker** to ensure the solution is packaged in a container for making it platform independent .
*   Test the system completely offline to guarantee it is securely deployable in an air-gapped network .
*   Push the final standardized, lossless, analytics-ready representation directly into the enterprise's next-generation SIEM and cybersecurity platforms .

## The Tech Stack

| **Ingestion Engine** | Vector or Fluent Bit | Crazy fast and handles the massive volume of billions of events per day without breaking a sweat .
| **Message Broker** | Apache Kafka | Acts as a shock absorber for the Big Data environments so the parsing engine isn't overwhelmed .
| **Common Schema** | Elastic Common Schema (ECS) | Gives us a ready-made, open-source standard to normalize fields into a common event taxonomy .
| **Parsing Logic** | Python / Go | Perfect for writing the plug-and-play onboarding scripts for new log sources .
| **Containerization** | Docker / Kubernetes | Packages the solution in a container to make it platform-independent and air-gapped ready .
