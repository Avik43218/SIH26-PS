# PS26159 — Email TLS/STARTTLS Security Analyzer

An AI-assisted tool that inspects PCAP captures of email server traffic (SMTP, IMAP, POP3) and automatically scores how secure the encryption setup is — **without decrypting anything**.

## Background

A PCAP file is essentially a recording of network traffic — data traveling over a network is broken into small packets, and tools like Wireshark let you open a PCAP to see every packet: who sent/received it, what protocol was used, and the content itself (if unencrypted). For this project, the tool analyzes traffic captured from an email server to figure out what happened during each session.

**Relevant email protocols:**

| Protocol | Purpose |
|---|---|
| SMTP | Sending email |
| IMAP | Reading/syncing email across devices (e.g. same inbox on phone and laptop) |
| POP3 | Older method — traditionally downloads and deletes mail from the server; less common now that multi-device sync is preferred |

**TLS** is the encryption layer that turns readable network traffic into unreadable traffic so only the recipient can decode it (HTTPS = HTTP + TLS). Before TLS starts, there's a **handshake** — a negotiation where both sides agree on an encryption method, exchange cryptographic keys, and verify identity via a certificate. The handshake itself is unencrypted even though the resulting session is, which is exactly what this tool inspects.

SMTP, IMAP, and POP3 start out unencrypted and switch to TLS mid-session via the **STARTTLS** command. Detecting that exact switching moment is critical, since everything after it must be analyzed as encrypted rather than plaintext.

## Problem Statement

Email servers use TLS/STARTTLS to encrypt communication, but many real-world setups still run outdated or weak encryption (old TLS versions, weak ciphers, expired certificates). Checking this today requires a security analyst manually inspecting packet captures. This tool automates that inspection and adds risk-scoring on top.

A weak TLS setup can be silently exploited (downgrade attacks, MITM, interception). Existing tools like Wireshark show the packets but don't assess risk or prioritize what to fix first — that's the gap this project fills.

**Important framing:** this tool works strictly with *metadata* from the encrypted handshake, never message content. It does not claim to break or read encrypted email.

## Pipeline Overview

1. **Input** — a PCAP file (captured network traffic)
2. **Protocol identification** — detect SMTP/IMAP/POP3 traffic by port (25, 143, 110, and their TLS variants)
3. **STARTTLS detection** — catch the plaintext-to-encrypted transition mid-session
4. **TCP stream reconstruction** — reassemble scattered packets into coherent conversations (standard network forensics, via tools like Scapy or dpkt)
5. **TLS handshake parsing** — extract TLS version, cipher suite, and key exchange method from the unencrypted handshake
6. **Certificate extraction & validation** — pull the X.509 certificate and check expiration, key length, signature algorithm, and chain validity
7. **AI/ML layer** — classify session risk (low/medium/high) and flag anomalies
8. **Output** — a security posture score, a prioritized vulnerability list, exportable reports (JSON/PDF/HTML), and a dashboard

### What the handshake reveals

- **TLS version negotiated** — TLS 1.0/1.1 = bad, TLS 1.2/1.3 = good
- **Cipher suite chosen** — some are weak/deprecated (RC4, DES, export ciphers)
- **Key exchange method** — is Forward Secrecy used? ECDHE = good, static RSA = bad

### What certificate validation checks

- Expiration date
- Key length (RSA-1024 = weak, RSA-2048+ / ECC = good)
- Signature algorithm (SHA-1 = weak, SHA-256+ = good)
- Certificate chain validity

### The AI/ML layer

- **Risk classification** — given extracted features (TLS version, cipher, cert age, key length, etc.), classify sessions as low/medium/high risk using a supervised classifier (Random Forest, XGBoost) trained on labeled examples of "good" vs "bad" configs.
- **Anomaly detection** — flag TLS sessions that behave unusually (unexpected cipher for a given server, sudden downgrade) using unsupervised methods like Isolation Forest or clustering.

| Layer | Tools |
|---|---|
| Packet parsing | Python — Scapy, dpkt, or pyshark (wraps tshark) |
| TLS/cert analysis | `cryptography` library or pyOpenSSL |

## Key Challenges

- **Genuinely technical/niche domain** — real understanding of TLS handshakes and STARTTLS is required; this isn't something to fake in front of judges who know security.
- **Getting realistic PCAP data** — sample PCAPs with SMTP/IMAP/STARTTLS traffic are needed. Public datasets exist (e.g. Netresec), or generate your own with test mail servers + Wireshark.
- **Justifying the "AI"** — a lot of the core checks (TLS version, weak ciphers) are rule-based/deterministic, not ML. The risk-scoring/anomaly-detection piece needs to be genuinely learned from data, not if-else logic dressed up as ML.
- **No content decryption** — the tool only works with metadata from the encrypted handshake, never message content. Framing this correctly matters so it doesn't look like a claim to break encryption.

This problem statement leans security/networking-heavy rather than typical web-app dev. A standard full-stack team will need to lean more on backend/packet-parsing work, while the frontend role mainly owns the dashboard/visualization layer.

## Implementation Steps in Detail

### 1. Get PCAP data to work with

Real email traffic isn't available, so generate your own test data:

- Spin up a local mail server with STARTTLS enabled — easiest via a Docker image like `docker-mailserver`, or a Postfix + Dovecot setup with a self-signed certificate.
- Send test emails using Python's `smtplib` (calling `starttls()`) or a real client like Thunderbird pointed at the local server.
- Capture traffic with **Wireshark** (GUI) or **tcpdump** (CLI):
  ```bash
  tcpdump -i lo -w capture.pcap port 25
  ```
- Repeat for IMAP (port 143) and POP3 (port 110), and capture both weak configs (old TLS/self-signed certs) and strong configs (TLS 1.3) so the tool has something to flag.

This gives full control and known ground truth — the exact TLS version/cipher configured is already known, which is also useful for validating the ML model later.

### 2. Protocol identification

**Use:** `pyshark` (a Python wrapper around tshark/Wireshark's engine) rather than writing packet dissection from scratch.

**How:** Filter by port as a first pass (25/587 → SMTP, 143/993 → IMAP, 110/995 → POP3), then confirm via protocol-specific plaintext commands in the payload (`EHLO`, `AUTH`, `220` responses for SMTP; `a1 LOGIN`, `* OK` for IMAP).

```python
import pyshark

cap = pyshark.FileCapture('capture.pcap')

for pkt in cap:
    if hasattr(pkt, 'tcp') and pkt.tcp.dstport == '25':
        # likely SMTP
        pass
```

### 3. STARTTLS detection

**How:** Within each TCP stream, scan the plaintext packets for the literal `STARTTLS` command from the client and the server's positive response (`220` for SMTP, `a1 OK` for IMAP). Mark the packet index where this happens — everything after that point in the same stream is treated as encrypted TLS, not plaintext protocol commands.

This stage is essentially string matching on decoded payload bytes — no special library needed beyond the packet reader already in use.

For plain SMTP/IMAP/POP3, plaintext commands (`EHLO`, `LOGIN`, etc.) act as a backup confirmation alongside port number. For the "S" variants (SMTPS/IMAPS/POP3S), that backup doesn't exist — the very first packet after the TCP handshake is already encrypted TLS data, so port number (465/993/995) becomes the *only* signal for identifying protocol type.

### 4. TCP stream reconstruction

**Use:** `tshark` directly — it has built-in stream following.

**How:** Every TCP connection has a unique 4-tuple (src IP, src port, dst IP, dst port). Group packets by this tuple, order by sequence number, and reassemble.

```bash
tshark -r capture.pcap -q -z follow,tcp,raw,0
```

This returns a session's reassembled bytes directly, with no manual sequence-number math needed. `pyshark` can also iterate by `tcp.stream` index to group packets programmatically.

### 5. TLS handshake parsing

**Use:** `tshark` — it already fully understands TLS handshake structure, so there's no need to hand-roll a TLS parser.

**How:** Export handshake fields directly as JSON:

```bash
tshark -r capture.pcap -Y "tls.handshake" -T json > handshake.json
```

This provides `tls.handshake.version`, `tls.handshake.ciphersuite`, `tls.handshake.extensions_key_share` (indicates whether forward secrecy/ECDHE was used), and more — all pre-parsed. `pyshark` exposes the same fields as packet attributes for a programmatic approach.

### 6. Certificate extraction & validation

**How:** The certificate is inside the Certificate handshake message; `tshark` can dump it as raw DER bytes (`tls.handshake.certificate` field). Once extracted:

**Use:** Python's `cryptography` library to parse and inspect it.

```python
from cryptography import x509

cert = x509.load_der_x509_certificate(cert_bytes)

cert.not_valid_after                      # expiry check
cert.public_key().key_size                # key length
cert.signature_hash_algorithm.name        # e.g. sha1 = weak, sha256 = fine
```

For chain validation (self-signed vs. trusted), `certvalidator` or `pyOpenSSL` can check against a root CA bundle — but for a hackathon demo, flagging "self-signed" and "expired" covers most of what judges want to see.

### 7. Feature extraction (bridge to ML)

**How:** For every session, build one row of structured features:

```
tls_version, cipher_strength_score, key_length, cert_expired (bool),
self_signed (bool), forward_secrecy (bool), days_until_expiry,
signature_algo_weak (bool)
```

This becomes the ML input table — a Pandas DataFrame works well.

### 8. AI/ML risk scoring

**How:** Without a large labeled real-world dataset, generate labels from known security standards as ground truth (NIST/OWASP guidance, e.g.: TLS < 1.2 = high risk, RSA < 2048-bit = high risk, expired cert = high risk). This programmatically labels the simulated sessions, and a classifier is then trained on top so the result is genuinely learned rather than pure if-else logic — satisfying the "AI" requirement of the problem statement.

**Use:** scikit-learn — `RandomForestClassifier` for risk-tier classification (low/medium/high), and optionally `IsolationForest` for flagging anomalous sessions (unsupervised, no labels needed).

### 9. Report generation

**Use:** `jinja2` for HTML templating, `WeasyPrint` or `reportlab` to convert to PDF, and plain `json.dump()` for JSON export. This is straightforward output formatting once risk-scored results exist.

### 10. Dashboard (frontend)

**How:** The backend (likely FastAPI) exposes an endpoint that takes a PCAP upload, runs steps 2–9, and returns a JSON result. The frontend covers:

- Upload component for the PCAP file
- Table/list of detected sessions with color-coded risk badges
- Detail panel per session (TLS version, cipher, cert info)
- Aggregate charts (Recharts) — e.g. risk distribution, TLS version breakdown
- Export buttons hitting the report endpoints
